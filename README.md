# Лабораторна: профілювання, SIMD-оптимізація та енергоспоживання

## 1. Програма
`lab.cpp`: функція `process_data` обчислює `c[i] = a[i]*b[i] + a[i]/2.5f - b[i]*1.1f`
для трьох масивів по 100 000 000 `float` (≈400 МБ кожен), 10 ітерацій.
Програма однопотокова.

Збірка (`make`):
- unopt: `g++ -O0 -g -fno-omit-frame-pointer`
- opt:   `g++ -O3 -march=native -g -fno-omit-frame-pointer`
- асемблер: `make asm` (`lab_unopt.s`, `lab_opt.s`)

Файли: `lab.cpp, `Makefile, flamegraph_unopt.svg`, `flamegraph_opt.svg`, `lab_unopt.s`, `lab_opt.s`.

Відео-захист: https://youtu.be/3pnRe33JtPU

## 2. Результати

| Показник | -O0 | -O3 -march=native |
|---|---|---|
| Elapsed (wall) | ≈2,24 с (`perf stat`) | ≈0,40–0,46 с (`time` / `perf stat`) |
| User time | 1,80 с | 0,10 с |
| System time | 0,30 с | 0,30 с |
| CPU usage | 99 % | 100 % |
| Max RSS | ≈1,17 ГБ | ≈1,17 ГБ |
| Minor page faults | ≈293 тис. | ≈293 тис. |
| Інструкцій / циклів (`perf stat -d`) | ≈45,4 млрд / ≈9,2 млрд | не знімалось |
| IPC | ≈5,0 | не знімався |
| Енергія пакета CPU (`energy-pkg`) | не знімалась | ≈18,45 Дж за ≈0,46 с (≈40 Вт) |
| Частка `process_data` у FlameGraph | 87,86 % | 9,54 % |
| Усього семплів у FlameGraph | ≈106 млн | ≈20 млн |

Прискорення за часом: ≈5 разів.

## 3. Інтерпретація

### 3.1 FlameGraph (пп. 1, 4.3)
Побудова: `perf record -g ./lab` → `perf script | stackcollapse-perf.pl | flamegraph.pl > *.svg`
(збірка з `-g -fno-omit-frame-pointer`, щоб стеки були повні).

- **-O0:** майже весь графік (≈88 %) — це `main → process_data`. Програма
  більшість часу виконує обчислювальний цикл, де кожен елемент обробляється
  скалярно, з багатьма зайвими зверненнями до стеку.
- **-O3:** `process_data` стискається до ≈9,5 %. Загальна кількість семплів
  зменшилась приблизно в 5 разів (≈106 → ≈20 млн), що відповідає
  зменшенню часу. Тепер на графіку помітні інші частини: ініціалізація
  масивів у `main` і «башти» ядра (page faults при першому зверненні до
  ≈1,2 ГБ пам'яті). «Гарячою точкою» стала вже не обчислювальна функція,
  а робота з пам'яттю.

### 3.2 `/usr/bin/time -v` (п. 2.1)
- `Percent of CPU ≈ 100 %` — програма однопотокова, одне ядро.
- `Maximum resident set size ≈ 1,17 ГБ` = 3 масиви × 400 МБ (`new float[n]`).
- `Minor page faults ≈ 293 тис.` ≈ 1,17 ГБ / 4 КБ: кожна сторінка вперше
  торкається під час ініціалізації. Оптимізація цього **не змінює**.
- Major faults = 0, swap = 0 — оперативної пам'яті вистачає.
- **System time однаковий (0,30 с) в обох версіях** — це обробка page faults
  ядром. User time впав з 1,80 до 0,10 с — це сам виграш від оптимізації коду.
  Тому в оптимізованій програмі приблизно ¾ часу припадає на системну
  частину (виділення пам'яті), яку компілятор прискорити не може.

### 3.3 `perf stat -d` (п. 2.2), версія -O0
- `instructions` ≈ 45,4 млрд, `cycles` ≈ 9,2 млрд при частоті ≈ 4,1 GHz.
- **IPC ≈ 5,0** — дуже високий, але це не ознака ефективності. Неоптимізований
  код складається з великої кількості простих `mov` зі стеком (load/store),
  які ядро виконує паралельно. ≈45 інструкцій на елемент
  (45,4 млрд / 10 ітерацій × 100 млн елементів) — це дуже багато для одного
  виразу. Тому для порівняння версій важливіші час і кількість
  інструкцій, а не сам IPC.
- `branch-misses` практично нуль (≈0,23 млн на ≈1,4 млрд переходів):
  цикл простий і добре передбачуваний.
- `L1-dcache-load-misses` і `LLC-loads` показують, що дані проходять
  крізь кеші потоком: масиви (≈1,2 ГБ) набагато більші за кеш,
  кожен елемент читається один раз за ітерацію.
- Для `-O3` `perf stat -d` не знімався, тож порівняння за цими лічильниками
  не наводжу (порівняння виконано за часом, `time -v` і FlameGraph).

### 3.4 `perf record / report` (п. 2.3)
- У звіті домінує `process_data(float*, float*, float*, int)`, а також
  `main` (ініціалізація). Частина стеків має символи `unknown` — це
  обмеження доступу до ядра (`kptr_restrict`), на висновки не впливає.

### 3.5 Асемблер (пп. 4.1, 4.1.1)
- **-O0:** скалярні інструкції `mulss xmm1, xmm0` тощо
  (`movss`, `mulss`, `divss`, `subss`). Одна інструкція обробляє **1** `float`;
  значення постійно зберігаються і зчитуються зі стеку.
- **-O3 -march=native:** автовекторизація AVX/AVX2: `vbroadcastss`
  (константи 2.5 і 1.1 розмножуються по 8 елементах `ymm`),
  `vmovups ymm` (завантаження 8 `float` за раз), `vmulps ymm2, ymm0, ymm5`,
  `vdivps`, `vsubps`. Одна інструкція обробляє **8** `float`
  (256-бітний регістр); проміжні значення живуть у регістрах, а не на стеку.
- Теоретичне прискорення обчислень до 8×, фактичне загальне ≈5×.

### 3.6 Чому не 8× (п. 4.2)
1. **Пропускна здатність пам'яті.** На кожен елемент 2 читання і 1 запис
   (12 байтів), арифметика майже безкоштовна, тож цикл упирається в RAM.
2. **Закон Амдала.** Ініціалізація масивів і page faults (system time 0,3 с)
   не прискорюються і складають велику частку часу `-O3` версії.
3. `vdivps` — відносно повільна інструкція навіть у векторній формі.

### 3.7 Енергоспоживання (п. 3, 4.4)
- Виміряно: `sudo perf stat -e power/energy-pkg/ ./lab_opt` ≈ **18,45 Дж**
  за ≈0,46 с, середня потужність пакета ≈ **40 Вт**. Це RAPL-лічильник
  всього CPU-пакета (system-wide), тому включає також фонові процеси системи.
- Для `-O0` вимір енергії **не виконувався**. Орієнтовна **оцінка** (не вимір):
  при подібній потужності ≈40 Вт, ≈2,24 с × 40 Вт ≈ 90 Дж, тобто
  економія енергії порядку ≈5×.
- Причина: енергія = потужність × час. Миттєва потужність, імовірно,
  змінилась мало, а час скоротився приблизно в 5 разів, тому сумарна
  енергія нижча («race to idle»: швидше завершили роботу, швидше
  повернулись у стан спокою).

## 4. Висновки
1. `-O3 -march=native` прискорила програму приблизно в 5 разів
   (≈2,24 → ≈0,4–0,46 с) завдяки автовекторизації AVX (8 `float` за інструкцію)
   і оптимізації роботи з регістрами замість стеку.
2. `time -v`: user time впав з 1,80 до 0,10 с, а system time (page faults)
   лишився 0,30 с — оптимізація компілятора не впливає на витрати ядра.
3. FlameGraph показав зміну вузького місця: з обчислювального `process_data`
   (≈88 %) на ініціалізацію і роботу з пам'яттю (page faults).
4. Прискорення менше за теоретичні 8×, бо задача обмежена пам'яттю
   і містить неприскорювану частину (закон Амдала).
5. Менший час виконання означає й менші енерговитрати
   (для `-O3` виміряно ≈18,45 Дж).
6. **Обмеження роботи:** енергію виміряно лише для оптимізованої версії
   (для `-O0` наведено оцінку), а `perf stat -d` знімався лише для `-O0`.
